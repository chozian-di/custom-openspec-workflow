# Proposal

## Why

Stock OpenSpec provides a lightweight spec-driven workflow. It does not provide a reusable user-level policy for deeper requirements discovery, testing expectations, human acceptance testing, context-conscious Apply work, verification, or safe archival behavior.

This change adds that policy for brownfield software development. It keeps OpenSpec's lightweight, fluid workflow and adds only narrow, supported guidance and user-level helpers. The result remains a customization of stock OpenSpec, not a replacement framework.

The package must minimize maintenance burden and remain resilient to future OpenSpec and Grill Me upgrades.

## Upstream boundary and release baseline

The change MUST use the stock `spec-driven` schema and the supported OpenSpec extension points:

- `openspec/config.yaml`.
- Per-artifact rules.
- `operations.apply.guidance`.
- `operations.archive.guidance`.
- User-level or custom skills.
- A small bootstrap mechanism.

The initial change MUST NOT fork `spec-driven`, modify OpenSpec source, modify generated `openspec-*` skills, shadow official OpenSpec commands, or create custom Apply, Verify, or Archive implementations. A later boundary change requires the feasibility callout below and a new decision.

Before implementation, determine the installed OpenSpec version and the current published release selected for this customization. Record the release used for design and testing. Inspect the source for that published release when upstream behavior needs review. Do not use arbitrary content from GitHub `main` as the baseline.

The customization MUST remain visibly separate from upstream OpenSpec. It MUST also leave the upstream Grill Me skill from `satya-janghu/agent-skills` unchanged.

## Mandatory pre-implementation feasibility callout

Before any implementation deliverable is created, the plan MUST compare every target requirement with stock `spec-driven`, supported project configuration, user-level skills, and a thin bootstrap.

The plan MUST record the evidence and result for each requirement. If a requirement cannot use those surfaces, the plan MUST name the requirement, explain the limitation, and stop for a new decision before introducing a custom schema, replacement command, custom lifecycle implementation, or other non-goal.

Configuration guidance is the required first option for Apply behavior. A custom Apply implementation requires separate evidence that supported configuration guidance is insufficient. This initial change does not cross that boundary.

## What Changes

- Add a reusable user-level package with a canonical policy or configuration source, `custom-openspec-init`, `custom-openspec-grill`, only necessary support scripts, and a practical `README.md`.
- Add a bootstrap helper that invokes normal OpenSpec initialization for new repositories and safely augments initialized repositories.
- Merge the package policy into `openspec/config.yaml` while retaining project context, project rules, user files, and other existing configuration.
- Enable the supported OpenSpec workflow or profile needed to make `/opsx:verify` available without replacing the generated Verify skill.
- Add a thin `custom-openspec-grill` adapter that delegates requirements questioning to the upstream Grill Me skill.
- Stage Grill output safely when no OpenSpec change exists, then attach traceable supplemental `grill.md` context to a named change.
- Add lifecycle guidance for Explore, Propose, Apply, Update, Verify, and Archive.
- Add task and test policy for coherent work, automated verification, non-TDD unit testing, and applicable human acceptance testing.
- Add guidance for UAT completion, explicit waiver, selective invalidation, Verify freshness, and Archive checks.
- Make the Grill Me compatibility check report actual dependency, staging, attachment, and idempotence evidence instead of hard-coded contract flags.
- Record why Human UAT does not apply when reliable automation covers the acceptance criterion, without creating an unrelated manual task.
- Document Git branch and worktree isolation, OpenSpec and Grill Me upgrade paths, quality expectations, non-goals, and the twelve validation scenarios.

## Package and bootstrap scope

The package MUST be reusable across repositories. A user MUST NOT need to copy policy files or skills into each project.

`custom-openspec-init` MUST:

1. Run or invoke normal `openspec init` behavior where initialization is needed.
2. Preserve files generated by OpenSpec.
3. Keep the target project on the stock `spec-driven` schema.
4. Enable the supported workflow or profile that provides `/opsx:verify`.
5. Merge the standard policy into `openspec/config.yaml`.
6. Preserve project-specific context and rules.
7. Avoid duplicate rules or guidance on repeated runs.
8. Be idempotent.
9. Validate the resulting configuration where the installed release supports validation.
10. Report the files and configuration entries that it changed.

The helper MUST NOT replace the `openspec` executable or present itself as upstream OpenSpec. An initialized repository MUST be extended without destructive reinitialization. Project-specific configuration MUST remain possible after setup.

After the helper starts applying customization changes, a preflight, merge, Verify enablement, or validation failure MUST restore files changed by that customization to their pre-run state. It MUST leave unrelated user changes untouched, report the rollback, and not leave a partial policy.

The implementation MUST discover the appropriate user-level skill and executable locations for the supported coding-agent host. It MUST NOT assume that all hosts use the same locations.

## Planning artifacts and implementation deliverables

The proposal, design, specifications, and `tasks.md` are planning artifacts. They define intent, scope, evidence, and implementation work. They are not the user-level package deliverables.

The implementation deliverables are the canonical policy source, `custom-openspec-init`, `custom-openspec-grill`, necessary support scripts, tests and fixtures, and `README.md`. Change-local `grill.md` is supplemental planning context, not a stock schema artifact. Verify is a workflow review, not a task or package artifact.

## Grill Me scope

`custom-openspec-grill` is a thin adapter. It complements OpenSpec Explore by using Grill Me for deeper requirements interrogation. Grill can surface user intent, constraints, assumptions, decisions, tradeoffs, ambiguities, non-goals, and open questions.

The adapter MUST delegate the question process to the installed upstream Grill Me skill. It MUST not copy Grill Me interrogation logic, fork Grill Me, or perform implementation work.

The adapter MUST produce or import supplemental context named `grill.md` with these sections:

- Intent.
- Constraints.
- Decisions.
- Assumptions Surfaced.
- Open Questions.
- Non-Goals or Out of Scope.

The context MUST distinguish resolved decisions from unresolved questions.

Grill is optional. The workflow MUST remain lightweight for trivial or already-specified changes. Users can use normal Explore or Propose without Grill.

When Grill runs before a change exists, the adapter MUST retain the source in a non-root staging location. It MUST not create an unrelated root-level `grill.md` or a custom schema artifact. The staging and later attachment process MUST preserve traceability, identify the source session, and avoid relying only on a fragile filename slug. When a named change exists, `grill.md` MUST live with that change or have an equally clear relationship to it.

When applicable `grill.md` context exists, proposal, specification, design, and task work MUST use its confirmed intent, constraints, decisions, resolved assumptions, non-goals, and open questions as supplemental planning input. It MUST remain separate from the stock schema artifact set.

The documented Grill Me compatibility check MUST discover the installed upstream skill and exercise the adapter's stage, attach, repeated-attach, traceability, required-section, optional-use, and no-implementation-work contract in isolated state. It MUST report actual results and MUST NOT claim delegation or implementation status from hard-coded values.

## Normal lifecycle

The final package `README.md` MUST document this lifecycle and include a clear diagram:

```text
Idea or problem
      |
      v
custom-openspec-grill, optional
      |
      v
grill.md, supplemental context
      |
      v
/opsx:explore, optional
      |
      v
/opsx:propose
      |
      v
/opsx:apply
      |
      +--> coherent implementation groups
      |        |
      |        +--> automated tests when applicable
      |        +--> re-anchor as needed
      |        +--> required UAT when applicable
      |
      +--> planning problem, /opsx:update, then /opsx:apply
      |
      v
/opsx:verify
      |
      +--> issue found, Apply or Update, affected UAT when invalidated,
           then Verify again
      |
      v
/opsx:archive
```

The normal ordering is Apply, required or waived UAT, Verify, then Archive. This order uses native incomplete-task protection for applicable UAT before the workflow-level Verify review. The lifecycle MUST preserve the OpenSpec distinction between implementation problems and planning problems.

## Apply versus Update

Use Apply when the proposal, specifications, or design remain correct and the implementation does not satisfy them. Examples include a coding defect, an implementation test failure, incorrect behavior against an existing requirement, or a missing task that does not change agreed intent.

Use Update when implementation shows that the proposal, specifications, or design are incomplete, incorrect, contradictory, or no longer describe the desired behavior. Examples include a newly discovered architectural constraint, omitted behavior, meaningful scope beyond the plan, or a changed user expectation.

The workflow MUST favor Apply, then Update when a planning problem is found, then Apply again. The user normally approves planning revisions through OpenSpec Update. The agent MUST not silently change planning intent during implementation.

## Task and test policy

The customization MUST use stock `tasks.md`. It MUST not add `verification.md` or a custom task scheduler.

Tasks MUST be grouped into coherent implementation areas. They can reflect dependency order and must be small enough to implement and check sensibly. The task format MUST not add static execution metadata such as worker assignments, scheduler waves, agent IDs, token estimates, mutex data, or parallel-safety labels.

For changed behavior that is reasonably unit-testable, tasks MUST add or update suitable unit tests. Test-Driven Development is not required. Tests do not need to precede implementation. Implementation followed by tests is valid.

The workflow MUST prefer project-native automated checks whenever behavior can be checked automatically. Suitable checks include unit, integration, functional, API, UI, browser, static analysis, lint, compilation, build, and other existing automated checks. Human acceptance work MUST not duplicate reliable automated verification.

## Human acceptance testing

Human UAT is required when applicable unless the user explicitly waives the specific scenario. It is limited to acceptance criteria that automation cannot reasonably or adequately establish, such as subjective appearance, interaction quality, UX expectations, human interpretation, unavailable hardware or environments, or user confirmation of intent.

Applicable UAT MUST appear in `tasks.md` as independent normal task checkboxes. Each independently invalidatable behavior MUST have its own task. A task can use durable labels such as `[x] HUMAN UAT - PASSED` or `[x] HUMAN UAT - WAIVED BY USER`.

When automation establishes every acceptance criterion, the workflow MUST record a concise reason such as `HUMAN UAT - NOT APPLICABLE: covered by <automated evidence>` in the task or acceptance record. This is evidence that UAT was considered, not a pass or a waiver, and MUST NOT create an unrelated manual task.

The agent MUST not self-pass UAT, infer acceptance, claim that manual acceptance occurred, or infer a waiver. Apply MUST pause at an outstanding UAT task and give the user manual steps and expected results. The user must explicitly pass or waive each scenario.

A Verify finding alone does not invalidate completed UAT. A later substantive implementation change can invalidate only the passed or waived scenarios that it could reasonably affect. A waiver applies only to the implementation state for which the user granted it. A relevant later change resets that waiver to incomplete.

## Verify and Archive

Verify is a workflow-level review, not a `tasks.md` checkbox. After all Apply tasks and applicable UAT tasks are resolved, Apply guidance MUST recommend `/opsx:verify` before Archive.

Verify MUST compare requirements, scenarios, tasks, automated test results, and applicable UAT results. A Verify result is fresh only for the substantive implementation state that it inspected. Any later substantive implementation change invalidates that result. A later change requires Apply, affected UAT when invalidated, and Verify again. A non-substantive change that cannot affect implementation correctness can retain the result, but uncertainty favors running Verify again. A Verify finding alone does not invalidate UAT.

Before Archive, the guidance MUST assess:

1. Normal implementation tasks are resolved.
2. Required Human UAT scenarios are passed or explicitly marked `WAIVED BY USER`.
3. No passed or waived UAT scenario was invalidated by later relevant implementation.
4. Verify covers the most recent substantive implementation state.

If Verify is missing, stale, or uncertain, the workflow MUST recommend Verify instead of Archive. If required UAT is incomplete, it MUST not recommend Archive by default. It can continue only after the user explicitly waives each named scenario, with the waiver recorded as `WAIVED BY USER`.

The guidance MUST retain normal OpenSpec incomplete-task protection. Any user-selected exception MUST be explicit and auditable.

## Guidance authority

Policy and operation guidance are advisory instructions. They direct the agent and user, but they do not hard-enforce behavior or replace native OpenSpec commands. Native schema behavior, command behavior, task tracking, Archive checks, and explicit user decisions remain authoritative.

The package and README MUST describe recommendations as recommendations. They MUST NOT claim that a guidance entry alone completed UAT, performed Verify, or made Archive safe when native OpenSpec or user evidence does not show that result.

## Git and source isolation

OpenSpec change isolation and source-code isolation are separate. Multiple change folders can be explored or planned at the same time. Change folders do not isolate source modifications.

When independent changes are both partially implemented, the README MUST recommend Git branches or worktrees as appropriate. Git remains responsible for branches, worktrees, commits, merges, rebases, and source conflict resolution. The customization MUST not automate branch or worktree management.

## Upgrade and maintenance strategy

The OpenSpec upgrade path MUST remain normal:

1. Upgrade to the desired published OpenSpec release.
2. Run normal `openspec update`.
3. Review release changes for configuration, skills, and workflows.
4. Confirm that the supported surfaces used by this package remain valid.
5. Run customization smoke tests.

Because the package does not fork `spec-driven`, it does not require a vendored schema diff or merge process unless a future change intentionally introduces a schema fork.

The Grill adapter MUST keep upstream Grill Me independently upgradeable. It must depend on the smallest practical public behavior contract, avoid assumptions about exact prose, line positions, or slug formatting, and prefer semantic extraction when output structure changes. The README MUST explain how to run a compatibility test after a Grill Me update, and the compatibility result MUST include actual dependency and attachment evidence.

## README scope

The package `README.md` MUST cover:

- Overview, including what is upstream and what is custom.
- User-level installation, bootstrap, host considerations, and the Grill Me prerequisite.
- New-project initialization.
- Grill use, non-use, its relationship to Explore, and `grill.md`.
- The full lifecycle diagram.
- Apply versus Update.
- Unit testing, no TDD requirement, automated verification, and residual-only UAT.
- UAT required when applicable, `PASSED`, `WAIVED BY USER`, `NOT APPLICABLE` with a reason, selective invalidation, and waiver invalidation.
- Verify ordering, scope, and freshness.
- The advisory nature of policy and operation guidance and the limits of hard enforcement.
- Lightweight and full re-anchoring.

- OpenSpec and Grill Me upgrade procedures.
- Troubleshooting for skipped or stale Verify, incomplete UAT, Archive with UAT outstanding, planning flaws, missing Grill output, and repeated bootstrap.

## Quality and non-goals

The customization itself MUST be small, understandable, version-controlled, idempotent where applicable, minimally coupled to OpenSpec and Grill Me internals, easy to remove, easy to inspect, explicit about changes, and conservative when overwriting project configuration. It MUST prefer simple scripts and configuration over complex orchestration.

The initial version MUST NOT implement:

- A custom OpenSpec schema.
- `verification.md`.
- A custom Apply skill.
- A custom Verify skill.
- A custom Archive implementation.
- A replacement lifecycle implementation.
- A task scheduler or CP-SAT scheduling.
- Fixed execution waves or static parallel-safe task annotations.
- Mandatory subagents.
- TDD enforcement.
- Automatic Git branch or worktree manipulation.
- Automatic UAT waiver.
- Modifications to upstream Grill Me.
- Modifications to upstream OpenSpec-generated skills.

If implementation shows that a non-goal is necessary, work MUST stop and the reason MUST be surfaced before that boundary changes.

## Validation plan

The implementation plan MUST use a disposable brownfield-style repository and test the customization itself. It MUST cover these twelve scenarios:

1. Simple change. A trivial change receives no unnecessary Grill or UAT ceremony.
2. Automated-only change. The path is Propose, Apply, automated tests, a recorded `HUMAN UAT - NOT APPLICABLE` reason, Verify, Archive.
3. Human UAT required. Independent UAT tasks are generated, Apply pauses for user input, the agent cannot self-pass them, and Verify follows completed Apply and UAT.
4. Explicit UAT waiver. The user can waive one scenario, the record says `WAIVED BY USER`, the record differs from `PASSED`, and Archive can proceed after the other checks.
5. UAT failure. The workflow distinguishes an implementation problem for Apply from a planning or expectation problem for Update, then Apply.
6. Verify discovers an issue. A Verify finding alone does not invalidate UAT. Substantive code changes invalidate the previous Verify, and only affected UAT is reopened.
7. Selective UAT invalidation. With several passed or waived scenarios, a change affecting one scenario reopens only that scenario.
8. Waiver invalidation. A later substantive change to waived behavior reopens the scenario instead of carrying the waiver forward silently.
9. Re-anchoring. Coherent task boundaries use lightweight re-anchoring, and meaningful interruption or Update uses full planning context without rereading everything after every task.
10. Premature Archive. Missing Verify, stale Verify, and outstanding required UAT each produce the designed Archive guidance.
11. Bootstrap idempotence. Repeated bootstrap runs do not duplicate policy, erase project context, or incorrectly overwrite stock files.
12. Upgrade smoke test. The package has a repeatable compatibility test after an OpenSpec or Grill Me upgrade that discovers the dependency and verifies isolated stage, attachment, repeated attachment, traceability, and no implementation work.

## Desired outcome

After installation, a user can enter a brownfield repository and initialize the customized OpenSpec environment with a user-level bootstrap. The result remains a normal stock `spec-driven` project with additional user policy.

The customization provides optional Grill Me discovery, normal Explore and Propose behavior, stronger task and testing expectations, non-TDD unit testing, automated-verification-first planning, Human UAT when applicable unless explicitly waived, auditable passed and waived UAT, selective UAT invalidation, context-conscious Apply with re-anchoring, optional host-native delegation, strongly expected Verify after Apply, Verify freshness rules, strong pre-Archive checks, safe Update loops, Git worktree guidance, and low upgrade and maintenance burden.

## Capabilities

### New Capabilities

- `user-level-openspec-policy`, for the reusable package, upstream boundary, release baseline, host integration, lifecycle documentation, upgrade guidance, quality requirements, and Git isolation guidance.
- `custom-openspec-init`, for safe new-project initialization and additive setup of existing projects.
- `custom-openspec-grill`, for optional upstream Grill Me delegation and traceable supplemental context.
- `openspec-lifecycle-guardrails`, for task, test, UAT, Apply, Update, re-anchor, Verify, and Archive guidance.

### Modified Capabilities

None. This change adds the user-level customization without changing an existing capability.

## Impact

The implementation will add user-level package files, a canonical policy source, a bootstrap helper, the thin Grill adapter, only necessary support scripts, and a comprehensive `README.md`. It will update target repositories through supported OpenSpec configuration and workflow surfaces while preserving project-owned configuration and upstream generated files.

Before implementation, the plan MUST complete the mandatory pre-implementation feasibility callout. It MUST explicitly record any requirement that the stock `spec-driven` schema, supported project configuration, user-level skills, and thin bootstrap cannot achieve. The implementation MUST not introduce a prohibited replacement or fork without first surfacing that limitation and receiving a new decision.
